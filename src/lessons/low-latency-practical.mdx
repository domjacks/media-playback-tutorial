## A Segment That Is Still Being Written

The live lesson waits until a 2 s segment is complete, then downloads it. The best case latency is therefore more than one segment duration plus the player buffer. Chunked CMAF removes the first part of that: the packager publishes the segment URL while the segment is still being produced, and the server sends each chunk as soon as it exists.

The test stream is DASH-IF livesim2 with two extra URL elements, `chunkdur_0.5` and `ato_1.5`:

`https://livesim2.dashif.org/livesim2/chunkdur_0.5/ato_1.5/testpic_2s/Manifest.mpd`

- `chunkdur_0.5` cuts each 2 s segment into four 0.5 s CMAF chunks, each one `moof`+`mdat`.
- `ato_1.5` sets `availabilityTimeOffset="1.5"` and `availabilityTimeComplete="false"` on the SegmentTemplate: segment N may be requested 1.5 s before it is complete, that is 0.5 s after it starts.
- The MPD also carries a `ServiceDescription` with a latency target of 3500 ms and a playback rate range of 0.96 to 1.04. This player uses both.

You can see the delivery with Node 18 or later, no player required. A request made 0.55 s into a segment returns `transfer-encoding: chunked`, and the body arrives in four steps about 0.5 s apart rather than all at once. Requested 0.3 s into a segment, the same URL returns `425 Too Early`.

## Split The Stream Into Chunks

`fetch` exposes the response as a stream: `response.body.getReader()` yields `Uint8Array` values as bytes arrive. Those network reads have no relationship to media chunk boundaries. One read may hold half a `moof`, or the end of one `mdat` and the start of the next `moof`.

MSE can in fact accept bytes split anywhere, so splitting is not about correctness. Appending only complete `moof`+`mdat` pairs is worth doing for three reasons: you make four appends per segment instead of dozens of tiny ones, each append is a decodable unit you can time and report, and a truncated response is detected instead of silently leaving half a chunk in the parser.

The splitter reads the 8-byte box header (size and four-character type, with a 16-byte form when size is 1), waits until the full box has arrived, and groups leading boxes such as `styp` with the `moof` and `mdat` that follow. An `mdat` closes a unit.

## The Streaming Loop

The loop mirrors the live controller but is driven by chunks rather than whole segments. It starts at the segment holding the time `live - target latency`, which is already complete, then waits for each following segment's first-chunk availability time and streams audio and video in parallel into their own SourceBuffers.

Each track has its own append queue, because audio and video chunks complete at different moments and `appendBuffer` calls on one SourceBuffer must not overlap.

<Snippet title="Chunk-By-Chunk Live Loop" explain="Wait until segmentAvailableAt, stream every track for the segment number, and append each unit as it arrives. A null result means the packager disagrees with our clock by a few milliseconds, so the same segment is retried. After the first segment the player seeks to the target playback time and starts maintenance. If one track returns null after the other has already appended, the retry re-appends the same time range, which is harmless." file="low-latency-practical/player.js" region="ll-loop" />

## Hold The Target With playbackRate

Latency is `livePresentationTime - video.currentTime`. The player samples it four times a second. Above the target it plays slightly faster, below it slightly slower, and the rate is clamped to the range the MPD publishes. A 0.15 s dead band stops the rate fluttering, and a buffer under 0.4 s forces the minimum rate whatever the latency says.

<Snippet title="Catch-Up Rate" explain="A proportional controller on the latency error, bounded by the ServiceDescription PlaybackRate range. <Exercise title="Estimate Throughput From Chunk Bursts">

The arrival log shows why naive throughput is wrong here: a segment of about 38 KB takes 2 s to download, which is 150 kbps, while the link may carry 20 Mbps. The time is spent waiting for the packager, not for the network.

Change the stream loop to estimate throughput per chunk instead. For each unit, divide its bytes by the time between its arrival and the previous unit's arrival, but only when the previous unit arrived less than 100 ms earlier (a burst). Log the estimate and compare it with the `bandwidth` declared in the MPD.

<Hint>Keep the arrival time of the previous unit inside streamSegment and pass the estimate to onUnit. Only the first chunk or two of a segment arrive as a burst, because they already existed when you asked. Later chunks are paced by the packager at one per 0.5 s, so they yield no usable sample. That is the core difficulty of throughput estimation for chunked delivery, and why chunk-aware ABR algorithms only trust the burst portions.</Hint>

</Exercise>
