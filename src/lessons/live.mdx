## Live Is Moving VOD

A live manifest changes over time. Segments expire from the back of the availability window and new segments appear near the live edge. The practical player needs to parse live MPD timing, turn wall-clock time into segment numbers, append missing segments, and prune old buffers.

The player should not chase the newest byte exactly. It should target a small latency behind live edge so downloads, CDN propagation, MSE append, and decode have room to recover.

- Parse live DASH timing fields instead of assuming first and last segment numbers exist.
- Start behind the live edge using suggestedPresentationDelay or a segment-count fallback.
- Start at the live edge with a segment cursor instead of downloading the whole time-shift window.
- Handle near-edge 404s as retryable and remove old buffered ranges after playback moves past them.
- After the first append, seek the video to the start of the buffered range and set mediaSource.duration to Infinity so the player treats the stream as live.

<Snippet title="Live Refresh Controller" explain="The controller refreshes the MPD, calculates the current window, and calls appendSegment(number) from a nextNumber cursor; that callback must fetch and append every track for that number. It starts at the live edge rather than the start of the time-shift window, jumps back to the edge if the cursor falls out of the window, and on a near-edge 404 stops for this tick without advancing so the same segment is retried. getNow lets the caller supply a server-corrected clock. fetchBytes attaches the HTTP status to the error it throws, which is what isNearLiveEdge404 inspects. Initialisation segments are appended once by the caller before start()." file="live/live.js" region="live-controller" />

<Snippet title="Near-Edge Retry" explain="A segment close to live edge can briefly 404 while it propagates through packaging and CDN layers. The check relies on error.status, which fetchBytes sets; fetch itself does not throw on a 404, so without that helper nothing would ever carry a status." file="live/live.js" region="near-edge-retry" />

<Snippet title="Start At The Live Media" explain="Appending media does not move the playhead. The first segment appended near the live edge starts at a large presentation time (here, seconds since 1970), so currentTime 0 is empty and the video waits forever. onStarted runs after the first append and moves currentTime to the start of the buffered range. Setting mediaSource.duration to Infinity marks the stream as live, and setLiveSeekableRange exposes the live window to the seek bar. Call it again as the window moves, and when audio and video are in separate SourceBuffers, call it once both have data." file="live/live.js" region="seek-to-live-start" />

<Snippet title="Wire The Live Player" explain="The real wiring: both SourceBuffers already exist and both init segments are appended. appendSegment fetches both tracks for a segment number before appending either, so a 404 on one track never leaves the other half-appended, and onStarted seeks to the live start. Appends and removals go through a small exclusive() queue so they never overlap on a SourceBuffer." file="live/player.js" region="live-wiring" />
